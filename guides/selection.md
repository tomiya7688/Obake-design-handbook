# 設計手法の選び方

[トップページ](../README.md) / [ガイド一覧](README.md) / 設計手法の選び方

設計手法は、名前が有名だから、使う技術が新しいからという理由だけで採用するものではありません。**自分のプロジェクトで何を改善したいのか**から考えます。

## 1. 困っていることを具体的にする

例えば「保守しづらい」だけでは、必要な手法を選びにくい状態です。

- 画面を変更すると、計算処理にも修正が必要になる
- 保存方法を変更すると、関係のない機能まで壊れる
- 処理の担当が曖昧で、どこをテストすればよいか分からない

このように、**何を変えたときに、どこで問題が起こるのか**を書き出します。

## 2. 手法が解決する問題と照らし合わせる

候補の手法について、次を確認します。

| 確認すること | 問いかけ |
| --- | --- |
| 目的 | その手法が解決しようとしている問題は、自分の問題と同じか |
| 条件 | このプロジェクトでも手法の前提を守れるか |
| 導入時の作業 | 役割分担、情報の受け渡し、テストなど、何を新しく決める必要があるか |
| 制約 | 今の技術や既存の設計と矛盾しないか |
| 効果の確認 | 採用後、何が改善されたと判断するか |

例えば、画面、アプリの判断、データの読み書きが混ざっているなら、[UPD Design](../methods/upd-design.md)が候補になります。これらの仕事を分けた後に、受け渡す値や失敗の知らせ方を決める必要があります。仕事の種類が少なく、今後もほとんど変わらない処理では、分けることで何が改善されるのかを確かめてください。

## 3. 小さな範囲で試す

候補を選んだら、既存の機能を1つ取り上げ、手法に沿って設計してみます。

試したあとに、「変更箇所が分かりやすくなったか」「テストしやすくなったか」「複雑さが増えすぎていないか」を確認します。

効果が確認できたら適用範囲を広げます。合わなければ、見送る、適用範囲を変える、ほかの手法を調べる、といった判断をします。

## 4. 採用後も理由を見直す

プロジェクトの規模、開発体制、必要な機能は変わります。以前は役立っていた手法でも、今の状況では不要になったり、見直しが必要になったりすることがあります。

採用時に「何を改善したくて選んだか」を短く記録しておくと、後から判断を見直しやすくなります。
