# UPD Design（UI・Process・Data 分離設計）

[トップページ](../README.md) / [設計手法の一覧](README.md) / UPD Design

**UPD Design は、アプリケーションの仕事を「UI」「Process」「Data」の3種類に分け、別の種類の仕事を混ぜないための設計手法です。**

画面を変更したら計算まで壊れたり、保存先を変更したら画面のコードまで直す必要が出たりする。そのような問題を減らすために、仕事の担当を明確にします。

このページでは、初めてUPDを知る人が、基本の仕組み、守る規則、採用に向く状況、実装の始め方を理解できることを目指します。

## 1. 何を解決するのか

例えば、購入ボタンを押したときの処理に、次の仕事がすべて書かれているとします。

- ボタンの操作を受け取る
- 購入できるか判断し、金額を計算する
- 注文をデータベースに保存する
- 成功や失敗を画面に表示する

この状態では、表示方法だけを変えたい場合でも、購入のルールや保存処理が書かれた部分に触れることになります。

UPDでは、**変更する理由が異なる仕事を分ける**ことで、修正する場所や確認する範囲を分かりやすくします。

## 2. 3つの層が担当する仕事

「層」とは、同じ種類の仕事を受け持つ部分をまとめた呼び方です。

| 層 | 担当する仕事 | 具体例 |
| --- | --- | --- |
| **UI** | 入力を受け取る、結果を見せる | ボタン操作、入力欄、画面表示 |
| **Process** | アプリのルールに基づいて判断・計算する | 割引額の計算、購入可能かの判定、ゲームの勝敗判定 |
| **Data** | データを取得・保存する | ファイルの読み書き、データベースへの保存、取得したデータの形式をそろえる |

重要なのは、フォルダやクラスの名前ではなく、**実際にどの仕事を担当しているか**です。

例えば、取得した価格の文字列 `"1200"` を数値に変換するのは、読み込んだデータの形式をそろえるDataの仕事です。その価格に会員割引を適用して金額を決めるのは、アプリのルールを扱うProcessの仕事です。

## 3. 守るべき境界

データを使う一般的な処理は、次のように仕事を受け渡します。

```text
要求：UI → Process → Data
結果：UI ← Process ← Data
```

UPDを採用する場合、次の境界を守ります。

- **UIは、アプリのルールの最終判断やデータの読み書きをしない。**
- **Processは、画面を直接操作したり、データの読み書きを自分で実行したりしない。**
- **Dataは、アプリのルールを判断したり、画面を操作したりしない。**
- **UIとDataを直接つながない。** 共通関数やイベントを間に置いても、実質的に直接やり取りするなら同じです。

これはすべての操作に3層を使うという意味ではありません。説明文を開閉するだけならUIで完結できます。データを使わない計算ならUIとProcessだけで足ります。

また、矢印は**仕事の受け渡し**を示しています。関数呼び出し、通知、非同期処理など、技術的な実現方法を固定するものではありません。

## 4. 具体例：商品を検索する

検索画面で、利用者がキーワードを入力して検索ボタンを押す場合を考えます。

| 順番 | 担当 | 行うこと |
| --- | --- | --- |
| 1 | UI | 検索欄からキーワードを受け取る |
| 2 | Process | 検索条件が有効か判断する |
| 3 | Data | 商品情報を取得し、必要ならデータの形式をそろえる |
| 4 | Process | 取得結果をアプリのルールに従って整理する |
| 5 | UI | 商品名などを画面に表示する |

例えば、検索結果の優先順位をアプリのルールで決めるならProcess、商品を表とカードのどちらで見せるかはUIが担当します。

検索条件が無効なら、Processがその結果をUIに返し、Dataに問い合わせずに終了してもかまいません。

### 実装の形を考える

次は、役割の違いだけを示した擬似コードです。特定の言語、クラス構成、通信方式を指定するものではありません。

```text
UI:
  キーワード = 検索欄から読み取る
  結果 = Process に検索を依頼する(キーワード)
  結果を画面に表示する

Process:
  キーワードが無効なら、その結果を返す
  商品一覧 = Data に取得を依頼する(キーワード)
  商品一覧をアプリのルールで並べる
  結果を UI に返す

Data:
  保存先から商品情報を取得する
  取得元によるデータ形式の違いをそろえる
  商品一覧を Process に返す
```

この擬似コードは、各層が何を担当するかを示しています。実際の関数の呼び出し方や、情報の受け渡し方は、使用する言語やプロジェクトに合わせて決められます。

注文を保存する場合にも同じ考え方を使います。**保存に失敗した事実**はDataが返し、**その失敗をアプリとしてどう扱うか**はProcessが決め、**利用者にどう知らせるか**はUIが決めます。「保存を依頼した」だけで「保存できた」と表示してはいけません。

## 5. 自分のプロジェクトに導入する手順

最初からアプリ全体を書き換える必要はありません。まず、商品検索や設定の保存など、流れを追いやすい機能を1つ選びます。

1. **仕事を書き出す。** 入力、表示、判断、計算、取得、保存などに分けます。
2. **担当する層を決める。** 仕事の名前ではなく、何のために行う処理かでUI・Process・Dataへ振り分けます。
3. **受け渡す情報を決める。** 例えば「検索文字を渡し、商品一覧か失敗を返す」と決めます。画面部品そのものやデータベース接続を別の層へ渡して、代わりに仕事をさせないようにします。
4. **各層を実装する。** フォルダ分割は補助になりますが、フォルダ名だけを変えてもUPDにはなりません。
5. **動作と境界を確認する。** 各層の処理を個別に確かめたうえで、層をまたぐ受け渡しと、失敗したときの動作も確認します。

既存のコードから始めるなら、まず「画面で行っている保存処理」や「データ取得処理に混ざったアプリの判断」を探すと、直す場所を見つけやすくなります。

## 6. どんなときに採用するか

### 向いている場合

- 画面、アプリのルール、データの保存方法を別々に変更する可能性がある
- 同じ処理を別の画面からも使いたい
- 不具合の調査やテストで、どの仕事に問題があるかを切り分けたい
- 複数人で開発し、担当する仕事の境界を共有したい

### 慎重に判断したい場合

- 入力を読み、少し加工して終わるだけの小さな一回限りのプログラム
- データ保存や画面表示を持たず、分割しても得られる効果が小さい処理
- 処理が単純で、仕事の担当を分けても、修正や確認をする場所があまり分かりやすくならない場合

UPDを導入すると、層の間で渡す情報、保存などに失敗したときの伝え方、層ごとのテスト方法を決める必要があります。こうした作業を行う理由は、担当外の仕事が混ざらないようにするためです。

採用するときはプログラムの大きさだけでなく、画面、アプリのルール、データの取得・保存が、それぞれ異なる理由で変更されるかを考えます。

## 7. 利点と注意点

| 期待できること | 注意すること |
| --- | --- |
| 変更箇所を探しやすくなる | 機能全体の仕様変更では複数の層を直す場合もある |
| 計算や判断を画面から切り離してテストしやすくなる | 層の間の連携も別にテストする必要がある |
| 表示方法や保存先を変えやすくなる | 受け渡す値や失敗の扱いを設計する必要がある |
| 開発時の役割分担を相談しやすくなる | 規則を守らないと、分割の効果が薄れる |

## 8. よくある誤解

**「UI・Process・Dataという名前のフォルダを作れば完成する」**

そうではありません。名前ではなく、実際の仕事が分かれている必要があります。

**「画面の操作は必ずDataまで通す」**

そうではありません。必要な層だけを使います。ただし、UIからDataへ直接つなぐことはしません。

**「間に共通の便利関数を入れれば、UIからDataを使ってもよい」**

そうではありません。仕事の境界を飛び越えていれば、間に部品を置いても違反です。

**「検査ツールが成功すれば、設計も正しい」**

そうとは限りません。ツールは一部の参照関係を検出できますが、計算がどの層に置かれているかなど、仕事の意味まで完全には判断できません。

## 9. 補助ツール

UPD Designの原典には[境界チェックツール](https://github.com/tomiya7688/upd-design/tree/main/tools)があります。これは、UI・Process・Dataの間で禁止されている参照を、一部のプログラミング言語で調べるためのツールです。

ただし、**検査に合格しても、仕事の分担がすべて正しいとは限りません。** 例えば、UIの内部に割引計算を書いても、層をまたぐ参照がなければツールだけでは見つけられない場合があります。コードを読むときも「その処理をどの層が担当するべきか」を確認してください。
